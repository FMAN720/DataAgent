# DeepSeek 连接测试误报修复

用户报告能获取 `deepseek-flash` 模型，但聊天测试反复显示笼统的地址/Key/模型错误。读取现有服务日志确认这些请求的供应商异常为 `BadRequestError`（HTTP 400），应用把它统一返回为 HTTP 502。没有读取、修改或再次使用用户的真实 Key 发起供应商请求。

## 原因与修复

[官方接口文档](https://api-docs.deepseek.com/api/create-chat-completion/)说明：默认开启思考模式，思考模式不支持 `required` 或指定函数的 `tool_choice`。原测试指定 `connection_check` 函数且没有显式关闭思考模式，构成已知的 400 请求参数冲突；原 32 Token 上限也过小。历史日志没有保留原始供应商错误正文，因此不把文档推断冒充原始报文证据。

- 连接测试改用与正常工具调用流程一致的 `tool_choice=auto`，输出预算为 256 Token，仍只有一次请求、不自动重试、不保存配置。
- 官方 `api.deepseek.com` 的默认请求明确使用非思考模式，避免测试和实际 Agent 工具循环依赖未实现的思考内容回传协议。用户显式指定模式时保留该选项；其他供应商不收到 DeepSeek 特有字段。
- 路由器保留安全的供应商 HTTP 状态/错误类别，不再丢失为一个通用 RuntimeError。连接测试区分参数 400、认证 401、余额 402、权限 403、路径/模型 404、限流 429、服务故障及网络/超时；仅使用固定诊断及允许列举的参数名，不回显原始异常、供应商正文、头部或 Key。
- 界面沿用现有错误显示，无布局或个人配置文件改写。

## 验证边界

新增 `tests/test_deepseek_compat.py` 使用真实 OpenAI SDK 和 MockTransport，覆盖 DeepSeek 风格的默认思考/强制工具冲突、测试不写配置、实际 ReAct 的两轮工具调用、其他供应商与显式模式不被覆盖，以及错误分类/脱敏/不重试。没有只用 FakeRouter 绕过 SDK 请求构造。

这批回归证明请求与错误处理符合已核对的兼容规则，不冒充用户账户的真实联网验证，也不保证供应商账户配额、实时可用性或所有模型的能力。此前 620 项测试未覆盖这条供应商默认模式规则，本轮已补上。

最终完整测试启用 PostgreSQL / Redis：**633 项通过，0 失败，57.78 秒**。真实 SDK 的新增兼容回归及个人模型测试共 28 项通过；Ruff 静态和 171 个文件格式检查通过，mypy 应用及评测共 110 个源文件通过。没有新增依赖、改写用户配置或发起付费模型请求。未修改前端布局或脚本；用户可保留当前窗口中输入的 Key，服务重启后直接再次测试。
