## 工具与使用方式

### 通用数据体检

`profile_dataset` 仅接受实际表和字段名称，标识符按数据库规则引用，不接受 SQL 表达式。PostgreSQL 限定在现有可见 schema 内。默认检查前 8 列，也可以指定最多 8 列；`columns_truncated` 会明确说明是否只检查部分列。

检查内容：

- 总行数、各列 NULL / 空白数量、缺失百分比及非 NULL 唯一值数。
- 数值列最小值、最大值、负值数量、非有效数值数量；保留原单位。
- 指定期望唯一键的重复多余行数，以及键字段缺失/空白行数。
- 日期字段观察到的最小/最大范围，以及请求周期是否超出该边界。

示例工具参数：

```json
{
  "table": "business.orders",
  "columns": ["order_id", "pay_amount"],
  "key_columns": ["order_id"],
  "date_column": "order_time",
  "expected_start": "2025-11-01",
  "expected_end": "2025-12-01"
}
```

SQLite 示例中表名使用 `orders`；上传表使用 `list_datasets` 返回的完整 `uploads.表名` 和实际列名。`key_columns` 只填写应当唯一的业务键，不能把区域、渠道等普通分组列当作唯一键。重复多余行数是各重复组 `count-1` 之和，不是重复组总行数。

所有统计使用数据库全量聚合，不把前几行样本当作全量质量结果。最多两条查询共用只读快照和既有总超时。空表、期望唯一键不可靠或请求超出日期边界时要求澄清；普通缺失、负数等展示警示。没有自动删行、填补、纠错或变更源文件。

### 版本化电商指标

`get_metric_definition` 可不传参数查看全部定义，也可传 `metric_id`。定义固定为版本 `1`、来源 `ecommerce_v1`：

| metric_id | 口径 | 输出单位 |
| --- | --- | --- |
| `net_sales` | paid / completed 订单实付金额之和，排除测试账号，整数分换算为元 | 元 |
| `order_count` | paid / completed 订单数，一行一单，排除测试账号 | 单 |
| `refund_rate` | refunded 订单数 / paid、completed、refunded 订单数，排除测试账号 | % |

时间统一按 `orders.order_time`，左闭右开。只允许 orders → users 的关联，先检查用户键唯一性，避免订单因一对多 JOIN 被重复累计。退款申请表不参与退款率，订单明细金额不替代订单实付金额。

`query_metric` 单周期示例：

```json
{
  "metric_id": "net_sales",
  "source": "ecommerce_v1",
  "start": "2025-11-01",
  "end": "2025-12-01",
  "dimension": "region"
}
```

双周期示例：

```json
{
  "metric_id": "net_sales",
  "source": "ecommerce_v1",
  "base_start": "2025-11-01",
  "base_end": "2025-12-01",
  "start": "2025-12-01",
  "end": "2026-01-01",
  "dimension": "region"
}
```

维度支持 `overall`、`region`（用户注册区域编码）、`order_channel`（下单端）。可选 `region_code` / `order_channel` 过滤同时应用到分组和独立总量。净销售额已经输出为元，不能再除以 100。比率为总分子/总分母，不平均各组比率；分母为零时值为 null，并明确未定义。

本轮没有将任意上传表自动映射成电商指标。上传表应先核对字段和单位，再通过通用只读查询分析。固定指标通过表结构、金额单位声明和数据检查验证既定契约，不能据此证明其他真实业务库的同名指标定义正确。

实际演示库的直接工具调用结果保存在 [offline-examples.json](offline-examples.json)：2025 年 11 月净销售额为 1,047,258.23 元，有效订单数为 1,039，退款率约 9.88725065%。区域对比通过分项与总量核对；请求“万元”时要求确认固定输出单位。示例未经过聊天模型。

## 前置检查和 Agent 行为

固定指标的首条查询检查全业务 orders/users 表中的重复键、关键缺失、未知状态、无效测试标记、无效标准下单时间、无法关联用户的订单；净销售额额外校验非负整数分和明确的“单位分”声明。不会把“未分摊”中的“分”误判为分币单位。

若检查失败，回调在数据库线程中中止后续统计，事务回滚并释放连接。通过后，分组与总量统计继续使用同一个快照。PostgreSQL 为 REPEATABLE READ + READ ONLY；SQLite 使用显式只读事务。快照接口限制最多 4 条语句，继承既有 SQL 只读检查、总超时、取消和行数限制；原有 `execute_many` 仍限制最多 2 条。

ReAct 对 `prepare_analysis` / `profile_dataset` / `query_metric` 先执行控制检查，体检/条件确认排在指标查询之前。出现错误或需要澄清时，同批其余工具不执行；明确需要澄清时直接返回问题，避免再调用模型生成未经核实的结论。后续一轮仍可在用户补充条件后继续。

新增的质量结果和指标结果纳入结构化证据。`analysis.quality_checks`、`analysis.metrics` 和原有 `comparisons` / `warnings` 在普通响应和 SSE final 中返回。现有前端能展示比较结果、质量警示和完整工具过程；本轮没有新增图表、导出或图片识别页面。

## 实际边界

日期最小/最大值只表示观察范围，不能证明没有漏日、漏单或导入延迟；尚未接入由业务方确认的入库完成水位。超出边界会要求确认，而不是断言一定缺数。通用体检对日期只检查边界，固定电商工具另有全量标准时间有效性检查。

固定指标检查全业务表，范围外的一条关键脏数据也会阻止统计。这是当前保守取舍，大规模数据应进一步研究按来源版本维护质量结果与入库水位；本轮没有添加质量缓存，也不缓存 SQL 结果。

程序约束适用于固定指标工具内部及同批控制步骤。通用 `run_sql` / 自由 SQL 形式的 `compare_periods` 继续保留，其业务语义仍需口径、提示和证据审查，不能宣称所有 SQL 均已获得机器语义证明。

429 项测试证明工程规则与这些用例下的行为，不等于真实问答准确率，也不证明模型一定会选择正确的工具。真实模型评测和费用收益仍需另行授权、运行及逐题复核；后续应为当前源码准备新的评测目录和指纹，不能将历史报告当作本轮效果。
