## 运行范围

- **数据：** 固定种子生成的合成电商库、15 份已提交的合成 Markdown、1 份合成 CSV；没有发送用户上传的资料。
- **模型：** 请求的是 DeepSeek `deepseek-chat` 和硅基流动 `BAAI/bge-m3`（1024 维）。**DeepSeek 返回的实际服务模型名是 `deepseek-flash`**，即服务商在 `deepseek-chat` 名下提供的模型，不是脚本可控制的。
- **计划：** 80 次问答 = 50 题基线 + 3 组消融各 10 题。实际完成 76 次：在"关闭审查"组第 7 题时，下一次请求的预算预留将超过 30 元上限，脚本按设计停止。剩余 4 题（`doc_appliance_cause`、`data_unit`、`safe_causal`、`safe_stock`）没有完成，其中第 7 题已有部分请求，但没有得到回答，已移到 `interrupted/`，不计入通过率。账本的保守估算累计为 29.69348 元，包含这道中断题已返回的请求。

## 失败的题

| 题目 | 现象 | 原因 |
|---|---|---|
| `cmp_regions` | 回答正确指出华南（SOUTH）下降最多，金额也对 | 判分要求在工具结果里找到"华南"字样，但库里存的是区域编码 `SOUTH`，中文名是模型翻译的。4 组都因此失败，属于判分规则过严，不是回答错误 |
| `cmp_south_app` | Agent 回复"该时间和筛选范围未找到业务订单"，要求澄清 | `query_metric` 的筛选组合没有匹配到订单，前置检查拦截后 Agent 没有换方式重查 |
| `doc_channel_meaning` | 问字段含义，Agent 却调用了固定指标工具，被日期边界检查拦下 | 工具选择错误 |
| `safe_future` | 问 2027 年数据，Agent 以"超出已观察数据范围"请求澄清 | 应直接说明"没有记录"，判分要求的措辞没有出现；行为本身没有把缺失说成 0 |
| `cmp_refund`（关闭审查组） | 要求确认 `source=ecommerce_v1` | 没有审查和修正环节时，前置检查要求澄清后直接结束 |
| `doc_appliance_cause`（关闭规划组） | 金额写成 23,492,775.00 元，标准答案是 234,927.75 元 | 把以"分"存储的明细金额当成了元，差 100 倍。审查判定不通过并修正了一次，复核仍未通过 |

后三类失败都和 `query_metric` 的前置检查有关：检查要求澄清时，Agent 倾向于把澄清问题原样抛给用户，而不是先自己换一种查询方式。这是下一步最值得改进的地方。

## 评测过程中修复的问题

1. **判分漏洞：** 判分原来只把 `run_sql`、`compare_periods` 的数字当证据，`query_metric` 和 `calculator` 给出的正确数字被判为"无证据"。5 题试跑中 4 题因此误判。已修复并补测试，试跑结果重新评分后 5/5。
2. **Windows 文件占用：** 写评测账本时 `os.replace` 偶尔报"拒绝访问"，异常从 HTTP 钩子抛出后被模型路由当成"模型不可用"，第二次全量运行在第 4 题中断。已改为短暂重试。
3. **第一次全量运行：** 建立合成文档向量索引时有一次 BGE-M3 请求没有返回（账本记录为 reserved），索引失败，没有发生聊天调用。重新运行时正常。
