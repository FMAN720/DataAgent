# 一周面试学习路线：电商数据分析 Agent

适用范围：基础一般、准备 AI 应用开发 / Agent 应用开发面试。按 2026-10-23 至 2026-10-29、每天 4 小时设计，共约 28 小时。没有具体 JD，先以 SQL Agent 为主线，RAG 为扩展；这是一周冲刺起点，不代表掌握整个后端或保证通过面试。

## 一周结束时要交付什么

- [ ] 不看稿，完成 60 秒项目介绍和 5 分钟架构讲解。
- [ ] 能从 HTTP 入口追到 SQL 执行，再追到最终响应。
- [ ] 能手写并解释净销售额、按区域汇总和退款率三条 SQL。
- [ ] 能解释并复现 SQL 错误反馈、口径不一致、虚构引用三个失败场景。
- [ ] 能说明 RAG 入库与查询两条流程，区分聊天模型与 Embedding。
- [ ] 如果核心进度允许，独立完成一个小改动，保留前后行为、代码和验证记录。
- [ ] 简历每个技术词都能展开，个人动作、AI 辅助部分和项目整体能力分开表述。

本周暂停新增中间件、框架迁移、模型训练和大规模效果实验。已有功能以学习和验证为主。本周练习不要求安装依赖或调用付费 API；如果自行运行真实聊天、上传并索引文档，会走真实外部模型，不能当成下面的离线练习。

## 每天的 4 小时怎么用

40 分钟补当天用到的基础，80 分钟沿调用链读代码，80 分钟动手或跟踪测试，30 分钟脱稿讲解，10 分钟记录问题。基础知识随代码补，不从头刷一整门 Python、数据库或机器学习课程。

读函数时只记录四项：输入、调用对象、状态变化、输出。遇到暂时不影响主线的细节先记下，每个问题最多卡 20 分钟。当天验收没通过，次日先用 30 分钟补齐，再缩减扩展项。

## 第 1 天：能运行、能看懂入口（10 月 23 日）

**目标：** 知道项目解决什么问题，一次请求从哪里进入。

**阅读顺序：** `app/main.py` 的 `build_agent()`，`app/models/schemas.py` 的 `AgentChatRequest` / `AgentChatResponse`，`app/api/routes/chat.py` 的 `chat()`。SSE 的队列和取消细节先看整体作用。

**只补这些基础：** 类与对象、函数调用、字典与 JSON、HTTP POST、参数校验；`async/await` 先理解为等待 I/O 时允许其他任务运行。

**练习：** 在项目目录运行已有离线脚本，它使用脚本模型和真实 SQLite 查询，不调用聊天或 Embedding API：

```powershell
.venv\Scripts\python.exe -m eval.phase6_offline --out reports/interview/offline-analysis-practice.json
```

打开生成文件，挑一条结果，找到 `question`、`answer`、`steps`、`analysis`、`reflection`。画出第一版请求图：浏览器 → 接口 → 编排器 → 工具 → 数据库 → 答案。

可选的离线界面预览：

```powershell
.venv\Scripts\python.exe -m eval.phase6_offline --serve --port 18081
```

打开 `http://127.0.0.1:18081/`，只使用以下脚本支持的场景：

- 比较 11 月和 12 月净销售额，按区域拆解
- 比较退款率，按下单渠道拆解
- 检查品类与净销售额的口径冲突
- 缺少条件：销售额为什么变化

预览中的回答和审查由脚本生成，不能演示为真实模型推理。它也不包含用户文档检索；正常工作台与离线预览要区分。

**当天产出：** 一张手绘架构图、一个请求样例、一段 60 秒项目介绍草稿。

**验收：** 能解释 `question`、`session_id`、`mode`，知道默认是 `react`，只有显式 `plan_execute` 才先规划；知道启动组装的对象不等于每次请求都重建模型和数据库连接池。

## 第 2 天：把数据和 SQL 讲明白（10 月 24 日）

**目标：** 不依赖模型也能解释分析结果从哪里来。

**阅读顺序：** `app/demo/glossary.md`；`app/analytics/tools.py` 的 `DescribeTablesTool`、`SearchGlossaryTool`、`RunSQLTool`；`tests/test_agent_loop.py` 的 `GOOD_SQL`；`app/analytics/engine.py` 的 `validate_readonly_sql()` 与 `execute()`。

**只补这些 SQL：** WHERE、JOIN、GROUP BY、SUM、COUNT、CASE WHEN、NULL；金额分转元、日期左闭右开、整数除法、测试账号过滤。

**练习：** 自己写三条查询：2025 年 12 月净销售额、12 月分区域净销售额、12 月退款率。逐条指出来源表、关联条件、订单状态、日期、单位和分母。先查结构，不凭记忆假设字段。可以在已有测试的 SQLite 临时库中，通过 `RunSQLTool` 或 `AnalyticsDatabase` 练习；不需要安装数据库客户端。

```powershell
.venv\Scripts\python.exe -m pytest tests/test_tools.py -q
```

再阅读一个只读 SQL 拦截测试，解释它为什么拒绝写操作。不要对真实业务表执行 DROP 或 DELETE 练习。

**当天产出：** 三条自己写的 SQL，每条配一段口径说明。

**验收：** 能解释净销售额与包含退款的 GMV 为什么不同，退款率为什么不能简单平均，为什么 JOIN 可能重复计算金额。若还不能独立写聚合与 JOIN，优先补本日内容，后面只学习 RAG 的概念流程。

## 第 3 天：吃透 ReAct 与 Function Calling（10 月 25 日）

**目标：** 能逐轮解释“SQL 出错后如何修正”。

**阅读顺序：** `tests/test_agent_loop.py::test_react_self_corrects_after_sql_error` → `app/core/agent/react_agent.py::ReActAgent.run` → `_parse_arguments` → `app/core/tools/registry.py::ToolRegistry.invoke`。

**练习：** 先单独运行已有场景，再在测试中设置断点，观察每轮 `messages`、`tool_calls`、`steps`：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_agent_loop.py::test_react_self_corrects_after_sql_error -q
```

手写这一轮消息顺序，并标明 `tool_call_id` 的对应关系：

```text
user 提问
assistant 返回工具名与参数
tool 返回结果或错误
assistant 根据结果继续调用工具
tool 返回修正后的查询结果
assistant 输出答案
```

再看参数 JSON 错误和最后一步收回工具的测试。区分三个层次：模型选择动作；程序检查并调用工具；数据库执行 SQL。模型返回的工具名本身不执行代码。

**当天产出：** 一张逐轮消息表、一次断点观察记录、2 分钟 SQL 自纠错口述。

**验收：** 能回答“工具是谁执行的”“工具结果为什么回传模型”“为何一次用户请求多次调用模型”“达到步数上限怎么办”。本日不通过时，暂停新增功能，优先讲透这一个循环。

## 第 4 天：可信分析、规划和审查（10 月 26 日）

**目标：** 说明项目怎样核对结果，以及核对能力的边界。

**阅读顺序：** `app/core/agent/orchestrator.py::_run` 的规划、执行、review、revision 和写回会话分支；`app/analytics/comparison.py` 的 `prepare_scope()` / `compare_results()` / `ComparePeriodsTool.execute()`；`app/analytics/engine.py::execute_many()`。

**练习：** 运行并解释以下既有场景：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_agent_loop.py::test_reflection_failure_triggers_one_revision tests/test_phase6_comparison.py::test_scope_mismatch_never_returns_contribution tests/test_phase6_evidence.py::test_clarification_stops_same_batch_sql_and_is_saved_for_followup -q
```

用纸算一个例子：A 区域从 100 降到 50，B 区域从 20 增到 40，整体从 120 降到 90。解释贡献为什么可能为负或超过 100%。再把独立整体改成 110，说明为什么核对失败时不能报告贡献。

理解同一事务快照的目的；比例分解本周只要求理解总分子/总分母和百分点，复杂对称分解公式留作加分。审查要能区分 passed、failed、unavailable、skipped；知道审查仍可能漏判，不能保证答案正确。

**当天产出：** 一段“口径冲突”故障故事，一张审查状态表。

**验收：** 能解释规则校验与模型审查的区别、为什么最多修正一次、为什么未通过或未完成审查的答案不作为可信事实写回历史。

## 第 5 天：RAG 最小闭环（10 月 27 日）

**目标：** 能把“文档怎么用于回答”讲完整。

**阅读顺序：** `app/etl/pipeline.py::run_bytes()`；`app/knowledge/service.py::search()` / `vector_search()`；`app/knowledge/embedding.py::APIEmbedder`；`app/knowledge/citations.py::collect_citations()`。Worker 本周只看职责，不逐行钻研租约实现。

**练习：** 分别画出两条流程：

```text
入库：文档 → 解析 → 分块 → Embedding → 向量入库
查询：问题 → 关键词/向量召回 → 阈值与排名融合 → 片段 → 模型回答 → 引用校验
```

```powershell
.venv\Scripts\python.exe -m pytest tests/test_phase3_citations.py -q
```

追踪虚构引用如何使回答失败，观察关键词检索、RRF 和上下文预算的测试。测试使用脚本模型或模拟数据，不调用真实 Embedding。不要将学习练习换成上传用户资料并建立真实向量索引。

**必须能区分：** 聊天模型生成答案，Embedding 生成向量；业务口径 `search_glossary` 当前走本地关键词检索，上传文档 `search_documents` 接入 BGE-M3/pgvector。当前没有可用向量索引时会避免无意义的查询向量调用。

**当天产出：** 两张流程图，以及“为什么选 pgvector、为什么混合检索、没答案怎么办”的回答草稿。

**验收：** 能解释分块、Embedding、余弦相似度、BM25、RRF 的作用，不要求推导；引用存在不等于结论正确。若进度不足，优先掌握两条流程与引用校验。

## 第 6 天：独立小改动、工程取舍和简历（10 月 28 日）

**当天产出：** 一项完成并验证的改动或诚实的调试记录；一份只保留自己能展开内容的简历项目段落。

## 第 7 天：完整模拟与演示预案（10 月 29 日）

**目标：** 从“看过”变成“能连续回答”。本日停止新学复杂模块。

建议用时：45 分钟完善 60 秒介绍；45 分钟脱稿画架构并讲 5 分钟；60 分钟连续追问；60 分钟修补最弱的两个点；30 分钟整理演示与备用材料。

**60 秒介绍结构：** 项目场景与定位 → 一条核心请求链路 → 两个关键设计 → 一项工程验证 → 自己的动作与当前限制。不要把全部功能逐条报出。

**连续追问清单：**

1. 你实际做了什么，现有基础和 AI 辅助部分是什么？
2. 为什么这是一条 Agent 循环？模型如何知道有哪些工具？
3. 工具调用参数是什么结构，由谁执行？
4. SQL 的错误如何进入下一轮模型输入？
5. SQL 能执行是否就代表口径正确？
6. 为什么数据库只读之外还要应用层校验？
7. 规划和 ReAct 如何衔接？默认每个请求都规划吗？
8. 审查失败、不可用和跳过有何区别？最多修正几次？
9. RAG 入库与查询分别怎样走？Embedding 与聊天模型有何区别？
10. 为什么混合检索仍可能误召回，引用校验能证明什么？
11. 服务重启后，文档、后台任务、会话与 trace 分别怎样？
12. 329 项测试和 50 题评测集分别能证明什么，哪些还没有实测？

每题先用 30～60 秒回答，再准备一个代码位置或实际例子。录音回听，找出“负责、优化、提升”等没有具体事实支撑的说法。

**演示准备：** 一条成功查询、一条错误修正、一条口径冲突；真实接口不可用时展示已准备的离线脚本、JSON 结果与对应代码，并明确离线模型是脚本。不要临时切换 Key、安装软件或依赖现场外部 API。准备材料时不展示 `.env`、数据库密码或真实用户文档。

## 面试中必须保持的事实边界

项目是本地个人实践与工程验证，尚无生产用户、业务收益或生产 SLA 证据。规划、执行与审查当前是共享模型路由器的角色模块，不宣称独立自治 Agent 协商。

2026-10-22 的最终记录为 329 项 Python 测试、6 项前端测试通过，12/12 SQL 跨数据库结果一致。50 题真实模型评测与消融尚未运行，不能说“50 题全部答对”或报告效果提升。测试通过率不等于真实模型准确率。

当前在线链路的会话和 trace 仍在进程内存中；不是已经实现多租户认证、多实例共享或全链路持久化。使用 API Embedding 不等于训练或研发模型。

## 时间不足时的压缩规则

每天只有 2 小时，或前三天进度落后时：保留第 1～3 天全部核心目标；第 4 天只掌握审查状态与口径冲突；第 5 天只掌握 RAG 两条流程与引用校验；第 6 天不强行做新功能；第 7 天模拟面试必须保留。简历收缩为自己掌握的 SQL Agent 主线，不把租约、复杂比例分解或消融写成个人重点贡献。

面试前可用 8 项自查：

- [ ] 能手写基本 JOIN 与聚合 SQL。
- [ ] 能找到请求入口并走到数据库执行。
- [ ] 能解释每种消息角色和工具调用对应关系。
- [ ] 能复现并解释一次 SQL 自纠错。
- [ ] 能解释只读约束、口径核对与审查的不同作用。
- [ ] 能画出 RAG 入库与查询流程。
- [ ] 能讲一个失败场景和一项真实个人动作。
- [ ] 能清楚区分已验证结果与尚未运行的模型评测。

如果时间必须二选一，优先把一个失败场景讲透，再扩充技术名词。第 1 天现在就从离线脚本和 `chat()` 的输入输出开始。
